# Solace Trading Lab

Deterministic trading infrastructure lab for order matching, market data, replay, and faults.
Runs a simulated venue over Solace PubSub+ with HTTP endpoints for local control.

## Run

```bash
uv sync
uv run pytest
```

```bash
./scripts/setup_solace.sh
./scripts/run_all.sh
```

Submit a resting order:

```bash
curl -X POST http://localhost:9001/orders \
  -H 'content-type: application/json' \
  -d '{"order_id":"sell-1","symbol":"FOO","side":"SELL","quantity":10,"price":"100.00"}'
```

Inspect venue state:

```bash
curl http://localhost:9001/book/FOO
```

## Performance Benchmarks

This repo includes deterministic CI checks plus opt-in Solace PubSub+/SDKPerf runs for local
Docker, TLS, and broker fan-out experiments. The public reference targets are from Solace's
software ESXi benchmark tables and were measured with TLS enabled.

```bash
uv sync
./scripts/benchmark_solace.sh
```

Artifacts are written to `artifacts/perf/<run_id>/`:

- `sdkperf_results.csv`: SDKPerf direct/persistent P2P and fan-out results
- `sdkperf_throughput.png`: Plotly comparison of local throughput vs. Solace targets
- `http_burst.csv`: venue HTTP burst latency and loss accounting
- `chaos_latency.csv`: deterministic replay tail-latency results
- `chaos_tail_latency.png`: Plotly p99/p99.9 latency vs. chaos/load
- `*.prom`: Prometheus text exposition for each chaos run

SDKPerf can be supplied either through `SDKPERF_BIN` or downloaded from a configurable URL:

```bash
SDKPERF_BIN=/path/to/sdkperf_java ./scripts/benchmark_solace.sh
STL_SDKPERF_URL=<sdkperf-download-url> ./scripts/benchmark_solace.sh
```

The script runs each SDKPerf case over plain SMF and SMF/TLS. For local self-signed TLS setups,
pass SDKPerf-specific TLS flags through `STL_SDKPERF_TLS_OPTS`.

Reference targets used by the benchmark harness:

| Msg Type | Pattern | Size | Fan-out | Solace Software ESXi |
| --- | --- | ---: | ---: | ---: |
| Direct | P2P | 100B | 1 | 2.5M msg/sec |
| Direct | Fan-out | 100B | 10 | 8.8M msg/sec |
| Persistent | P2P | 1KB | 1 | 170K msg/sec |
| Persistent | Fan-out | 1KB | 10 | 820K msg/sec |

## HFT Lessons

- Use Direct messaging for market-data fan-out when loss recovery is handled above transport and
  the dominant constraint is CPU for small messages or egress bandwidth for larger fan-out.
- Use persistent messaging for fills and execution reports where replayability and at-least-once
  delivery matter more than raw message rate.
- Tail latency is the trading risk. `src/chaos/benchmark.py` models persistent ACK/IOPS pressure
  and reports p99/p99.9 order-to-fill latency under deterministic replay load.
- Docker numbers are useful for regression and operator ergonomics, not bare-metal claims. Treat
  Solace ESXi targets as a reference envelope and run SDKPerf on pinned CPU, tuned NIC, and real
  storage before making production capacity decisions.

## Architecture

```text
                +------------------+
                | Solace PubSub+   |
                +------------------+
                  ^      ^      ^
                  |      |      |
+----------+   orders   fills   book     +-------------+
| Strategy | ---------> Venue ----------> | Market Data |
+----------+             |                +-------------+
                         |
                      recorder
                         |
                      replay
```

Core modules:

- `src/exchange/orderbook.py`: deterministic price-time priority book
- `src/exchange/matching_engine.py`: command routing and event publication
- `src/market_data/feed.py`: L1, L2, and trade-print projection
- `src/strategy/market_maker.py`: deterministic example strategy
- `src/replay`: JSONL recording and playback
- `src/chaos`: deterministic latency injection

## Extend

Add schemas in `src/common/models.py`, route topics through `src/common/config.py`, and keep
matching logic isolated from transport code. Use `InMemoryBroker` in tests and inject clocks for
deterministic assertions. Add scenario files under `scenarios/` for repeatable fault cases.
